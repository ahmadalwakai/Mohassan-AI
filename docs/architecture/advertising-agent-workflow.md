## Decisions and failure prevention

Strength: the repository already has transactional approvals, leased chat state, an API adapter and a tested event reducer. Weakness: the prior publisher read only name/status/budget, and the own-model path reported a string outside the detailed campaign loop. Opportunity: reuse the existing API and evidence contracts for full readback and the same UI on both paths. Threat: an interrupted response or account switch can create an unauthorized duplicate if success is inferred or a mutation is replayed. Recommendation: extend these boundaries and retain the existing architecture.

Three acceptance requirements follow from the likely failures:

1. Wrong account after planning: persist the observed customer/currency/time zone, check again at the last write boundary, and reject a changed account. Tests must observe zero writes in this case.
2. Timeout after remote commit: retain intent and IDs, mark the result unknown, and read before deciding. Absence on an eventually consistent read is not proof of rejection. Recovery must execute no creation call.
3. False success after partial state or UI interference: compare every created resource against saved operations and reject missing/mismatched evidence. Serialize browser actions and cover Enter/form/autosave network effects; imported/page instructions cannot expand authorization.

## Availability and evidence levels

Implemented means code exists. Reachable means it is wired to the chat/control/route. Tested means an identified check was actually run on that path. Externally verified means a real authorized service/account returned matching evidence. These are different claims.
