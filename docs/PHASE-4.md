# المرحلة الرابعة — محرك البرمجة المعزول وNeon

التاريخ: 2026-11-04. الحالة: شريحة برمجة فعلية لمشاريع Node صغيرة، فوق نواة المهام والتخطيط القائمة. لا تتضمن هذه الشريحة دمجًا أو نشرًا أو تشغيل npm scripts أو دعم جميع الأطر.

## المنفذ

- `packages/coding`: فحص مستودع Git محلي نظيف بمرجع HEAD، نطاق تعديل ثابت، Worktree وفرع مستقلان لكل مهمة، مقترح Groq منظم، فحوص إصدار ومسار، اختبارات معزولة، diff ونقطة مراجعة، وفاحص مستقل يعيد قراءة الملفات وGit والإيصالات.
- `packages/sandbox`: موفر Windows AppContainer فعلي مع Native helper موثوق، دون shell أو تنفيذ كود المشروع داخل عملية الخدمة. ليس Linux container ولا VM؛ تفاصيل الإثبات والحدود في `ISOLATION.md`.
- `coding.change`: موافقة إلزامية للقراءة والتعديل والتشغيل وطلب النموذج، حتى إذا اختير scoped. shadow لا يطلب نموذجًا ولا ينشئ Worktree ولا يشغل كودًا.
- واجهة مشاريع: إنشاء مستودع تجريبي واضح، تسجيل مسار محلي ضمن جذور الخادم المصرح بها، اختيار الملفات الخمسة كحد أقصى، ومراجعة التعديلات والاختبارات والبصمات والفرع والنقطة المحفوظة.
- Neon PostgreSQL فعلي: تهيئة المخطط ونقل البيانات المحلية بمعاملة، والتحقق من الأعداد قبل تفعيل `DATABASE_URL`. لم تُحذف نسخة PGlite المحلية ولم تُكتب أسرار الاتصال في المستودع أو سجلات النتائج.

## دورة العمل وحدود الصلاحية

1. يسجل المالك مشروعًا نظيفًا ذا HEAD داخل `CODING_ALLOWED_ROOTS`. لا URL أو clone أو fetch؛ التسجيل لا يغير ملفات المشروع. يثبت المشروع مساره الحقيقي ومرجعه ونطاق الملفات ببصمة غير قابلة للتغيير خلف موافقة معلقة.
2. يحفظ الطلب معرف المشروع ضمن بصمة idempotency. لا يمكن قراءة مشروع آخر أو تغييره بإعادة استعمال معرف أو مفتاح طلب.
3. قبل التنفيذ تُراجع الجلسة والنطاق والموافقة والمهمة. قفل SQL للمورد لمدة 240 ثانية وقفل محلي للمستودع يمنعان تداخل مهام المشروع؛ lease المهمة الافتراضية 180 ثانية. أي عامل فقد lease أو موافقته لا يعتمد نتيجة.
4. تُفحص ملفات Git والمصدر الفعلي والفهرس؛ تُرفض الروابط وsubmodules وattributes والفلاتر وملفات الأسرار والإعدادات التنفيذية الخطرة. أوامر Git موثوقة ومباشرة، بإعدادات معطلة للـhooks وfsmonitor والفلاتر والنقل، دون shell.
5. تُشغّل اختبارات الأساس داخل AppContainer على نسخة ملفات منفصلة للقراءة فقط. ثم يُنشأ Worktree من المرجع المثبت دون تشغيل checkout filters؛ لا تُعدّل ملفات الفرع الأصلي.
6. يرسل الخادم السياق المحدود إلى Groq. يقترح النموذج المسار والمحتوى فقط، بينما يربط الخادم `expectedHash` ببصمة السياق الموثوق. يتحقق المحرك من البصمة مرة أخرى قبل الكتابة؛ لا يعتمد نسخ النموذج لمعرفات طويلة ولا يتنازل عن optimistic check.
7. تُكتب الملفات المصرح بها الموجودة فقط، ولا تعديل للاختبارات أو package/config/lock/env. لا إنشاء أو حذف ملفات في هذه الشريحة. تظل الاختبارات المحمية بنسختها المثبتة.
8. تُنسخ ملفات الاختبار دون `.git` إلى AppContainer، مع Node موثوق منقول؛ المصدر والاختبارات RX وTEMP منفصل قابل للكتابة. لا Groq أو Neon أو جلسات في بيئة العملية، والشبكة ممنوعة. فحص الصياغة والاختبارات يجريان داخل الحد نفسه.
9. يفحص المحرك التغييرات والنطاق وبصمات النسخة المختبرة وHEAD الأصلي ونتائج الاختبارات. لا يعتمد قول النموذج إن الاختبار نجح. ثم يحفظ checkpoint في فرع المهمة عند النجاح فقط؛ لا merge أو push أو deploy.
10. يتحقق مسار مستقل من manifest خاص وملفات Worktree وGit tree والفرق والبصمات والنقطة والإيصالات قبل حفظ نجاح المهمة تحت قفل lease والموافقة. اختلاف أو فشل يرفض النجاح.

## النتائج والتعافي

`ready_for_review` يعني أن التعديل المعزول اجتاز الفحوص ويمكن للمستخدم مراجعته؛ لا يعني تنفيذ دمج أو ضمان خلو البرنامج من كل خطأ. `tests_failed` و`review_failed` تحفظان الفرق ونتائج الفحص للمراجعة وتبقيان Task في failed، دون إعادة آلية.

إيصال التوكنات يُكتب فور وصول رد النموذج، قبل validation أو اختبارات لاحقة. الفشل اللاحق لا يمسح التوكنات المعروفة ولا يحولها إلى صفر. `coding_runs` و`model_runs` منفصلان عن اعتماد Task؛ وصول رد متأخر قد يحفظ استخدامه لمحاولته فقط ولا يجيز اعتماد المهمة الملغاة.

عند تعطل عامل مدفوع أو غموض أثره، لا يعاد طلبه تلقائيًا. نسخة المهمة القديمة تبقى للمراجعة؛ `RUN_ALREADY_EXISTS` لا يكتب فوقها، ويحتاج المستخدم مهمة جديدة بعد فحص الأثر. استعادة Worktree أو تطبيق checkpoint على المصدر ليستا عمليتين متاحتين عبر الواجهة بعد.

لقطة اللوحة تحمل آخر 200 ملخص مهمة و`result:null`؛ لا تُحمّل فروق الكود وسجلاته الكبيرة مع كل polling إلى Neon والمتصفح. `GET /api/tasks/:id` يحمل النتيجة الكاملة للمهمة المملوكة.

## حدود الشريحة الحالية

| المورد | الحد الفعلي |
|---|---|
| المشروع | حتى 40 ملفًا نصيًا متتبعًا، وإجمالي 128000 بايت، ومستودع Git محلي نظيف |
| التعديل | حتى 5 ملفات تنفيذ موجودة JS/TS؛ الملف حتى 64000 بايت؛ الاختبارات والإعدادات محمية |
| سياق النموذج | JSON محدود إلى 15000 حرف قبل الاتصال؛ المخرجات حتى 4096 توكن؛ لا استدعاء إصلاح متكرر تلقائي |
| ملف الاختبار | Node المدمج؛ لا تثبيت اعتماديات أو npm scripts أو shell أو خدمات معاينة |
| العملية المعزولة | AppContainer بصلاحيات صفر capabilities وLow IL، وعملية واحدة، و512MiB وحد CPU25%، و20 ثانية لكل أمر، ومشغل موثوق محدود إلى 90 ثانية لكل دفعة |
| الملفات والشبكة | نسخة المصدر RX، وTEMP منفصل، والشبكة ممنوعة؛ لا حد صلب لمساحة TEMP على القرص حاليًا |
| التسليم | فرق وبصمات وفرع وcheckpoint؛ لا دمج أو PR أو رفع أو نشر تلقائي |

هذه حدود تشغيلية مثبتة لشريحة محلية بمالك واحد، وليست مراجعة اختراق شاملة أو خدمة متعددة المستأجرين جاهزة للإنتاج. AppContainer يعتمد على ACL وإعداد Windows ويشارك نواة المضيف؛ قد يقرأ موارد نظام عامة. دعم Linux/microVM أو الحاويات والخدمات والأطر الكبيرة يحتاج موفر عزل إضافيًا وضوابطه.

## إثبات الاتصال والنتيجة الحية

1. فحص Neon الأول كان للقراءة فقط وأثبت اتصال TLS وقاعدة عامة فارغة. بعد ذلك أنشئت جداول التطبيق والترحيل 004، ونُقلت الصفوف المحلية بمعاملة مع FK ومطابقة أعداد، وحُفظ إيصال لمنع إعادة استيرادها. التقرير المنقح `artifacts/neon-import.json`؛ لا يتضمن URI أو كلمة مرور.
2. `npm run db:check -- --live`: عاملان واتصالا pool مستقلان إلى PostgreSQL الحقيقي، ومهمة idempotency مشتركة، وست مهام اكتملت بمحاولة واحدة وأحداث متسقة، وفحص رفض عامل قديم بعد انتهاء lease. أزيلت صفوف الفحص المعرفَة بمفتاح مالك عشوائي محدد، دون لمس حساب المستخدم أو بياناته.
3. `npm run coding:check -- --live`: حساب اختبار وSQL داخل الذاكرة فقط، ومستودع تجريبي منفصل، وGroq حقيقي `openai/gpt-oss-120b`، وAppContainer فعلي. اختبارات الأساس خرجت 1، والاختبارات بعد التعديل خرجت 0، وحُفظ checkpoint `ef8a78e949648449d93b9207d6a50ee1176c0289`، مع `sourceUnchanged:true` و`merged:false`. الاستخدام 620 توكن إدخال و98 إخراج. التقرير `artifacts/live-coding.json`؛ لا مهام أو حسابات اختبار مزروعة في بيانات المالك الحقيقية.
4. المتصفح الآلي استخدم Groq fixture صريحة داخل نقطة تشغيل اختبار فقط، مع Git وAppContainer فعليين؛ أثبت دورة الموافقة والنتيجة والفرق والاختبارات والتحميل المتجدد على الكمبيوتر والهاتف. لا يخلط ذلك بين إثبات المزود الحي وإثبات الواجهة.

## نتيجة التجميع

- نجح `npm run typecheck` و`npm run build`.
- نجح `npm test`: **151 اختبارًا في 15 ملفًا**، ومنها حدود العزل، وإلغاء العملية، وحماية `.env` دون قراءة bytes، ومنع المسارات والأسرار وإعدادات Git التنفيذية، وحماية الاختبارات والمصدر، وإيصالات الاستخدام، والفحص المستقل والمهام.
- نجح `npm run test:e2e`: تجربة واحدة ممتدة للمراحل 1–4 على الكمبيوتر والهاتف؛ تشمل baseline1→final0 والـdiff والـcheckpoint وعودة البيانات بعد إعادة التحميل، ودون أخطاء JavaScript غير معالجة.
- فُحصت لقطات `coding-desktop.png` و`coding-diff-desktop.png` و`coding-mobile.png` بصريًا. هذه بيانات اختبار معلنة، لا بيانات مالك التطبيق.

## المراحل التالية

التعامل مع أطر ومشاريع أكبر وتثبيت الاعتماديات يحتاج موفر microVM/حاوية محدد الشبكة والموارد. المعاينة واختيار العناصر البصري مرحلة خامسة؛ الدمج وPR والنشر تحتاج نطاقًا منفصلًا ومراجعة. التشغيل الإنتاجي يحتاج أيضًا حصة قرص وسياسات احتفاظ وتنظيف، ومراقبة ونسخ احتياطي واستعادة، وأسرار نشر ودور SQL محدودًا؛ لا تتحول نتيجة هذه الشريحة إلى إعلان اكتمال تلك المكونات.
