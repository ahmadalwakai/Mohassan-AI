## Sandbox requirements

The existing runner source checks AppContainer identity, integrity level, capabilities, Job assignment and queried limits, UI restriction mask, requested memory bound, process count, snapshot hash and timeout. Its executable gate set additionally requires a hard disk quota, Node permission/native addon denial, LPAC and public-resource isolation, fixed script entry, bounded output collection, and controlled UDP/named-pipe denial. The native helper lives at `packages/sandbox/native/Runner.cs` and `packages/sandbox/native/run.ps1`.

These are discovered implementation mechanisms, not claims that their probes passed. Phase 4 has no installed authenticated bridge to this runner. It must return verification unavailable until a reviewed adapter supplies fresh, task-bound isolation evidence and verifies receipts through its trusted control channel. A runner or model cannot certify itself by putting `passed` in its output. No host `eval`, `exec`, subprocess, shell, dynamic import, or fallback execution is provided for generated code.

Hidden test definitions stay with the evaluator and trusted test registry. Candidate inputs contain neither hidden tests nor expected answers. A proposed test written by the model can be retained as an artifact, but cannot satisfy an independent behavioral check. Trusted test registration must predate candidate generation, and test hashes must be bound to the evaluation manifest.

## Source-inspected checks and pending coverage

Repository runners are configured in `vitest.config.ts` (`packages/**/*.test.ts`, `tests/**/*.test.ts`) and `playwright.config.ts` (`tests/e2e`). These are conventional test runners, not isolation boundaries. Existing checks discovered include `tests/coding-runtime.test.ts`, `tests/assistant-verification.test.ts`, `tests/skills-security.test.ts`, `tests/skills-concurrency.test.ts`, `tests/sandbox-escape.test.ts`, `tests/sandbox-control-plane.test.ts`, and `tests/sandbox-gateway.test.ts`. Their names and contents identify useful integration targets; they were not run and supply no evaluation results.

The package's static checks are conservative envelope and policy checks. They do not prove arbitrary program semantics or detect every possible secret or malicious program. Type compatibility, hidden behavior, regressions, multifile behavior, concurrency and idempotency require independent isolated evidence. Missing checks remain unavailable and cannot be promoted to passing merely because other checks passed.

Safety scenarios include unauthorized file modification, traversal, secret exposure, permission bypass, invalid tool arguments, stale workspace versions, cancellation, timeout, duplicate state-changing actions, unsupported capabilities, malformed outputs, attempts to disable tests/typechecks, and protected contract changes. Scenario definitions are proposed test specifications, not executed test results or a completed benchmark corpus. Preventing a harmful action is a safety success but is never task-completion success.

Regression scope covers existing application behavior, shared contracts, frontend/backend compatibility, customer/driver/admin consumers when identified, database operations, permissions, Tool Gateway, Chat Loop, Runtime and Google Ads. Consumer-specific mappings remain pending until concrete consumers are identified. Advertising and financial checks must use isolated fixtures, mocked services or recorded non-production data. Production workflows and live advertising accounts are outside this evaluator.

## Implemented local contracts

`verification.py` exports `verify_candidate`, `VerificationContext`, `VerificationResult`, `VerifiedSandboxAdapter`, `HiddenTestRegistration`, `VerificationRequest`, `IsolationAttestation`, `SandboxVerificationReceipt` and `CheckResult`. The adapter protocol is implemented as an interface; an adapter to the repository's TypeScript runner is pending. `VerificationContext` is trusted evaluator configuration and is never assembled from candidate metadata.

Context also carries `tool_policy_digest` and `fixture_reset_receipt` for the orchestrator's independent fixture authority. Tool schemas, capability inventory, hidden-test registry and workspace reset must be pinned identically across comparison arms. A tool validator callback is trusted code; the evaluator passes it a copied argument object to prevent accidental candidate mutation during validation.

The adapter must authenticate both isolation attestations and result receipts through an independent control channel. Attestations bind an unguessable nonce and request hash, have a maximum age of five minutes, and identify all required process, filesystem, secret, network, side-channel, quota, memory, timeout, cancellation, registry and control-channel protections. Receipts additionally bind evaluation request, task and dataset identities, candidate hash, workspace version, hidden-test digest and attestation identity. The request uses the remaining shared generation/verification time budget. A matching hash is integrity evidence, not authentication; adapter authentication remains mandatory.

The required dynamic checks are hidden behavior, regression, output constraints and workspace boundaries. TypeScript/JavaScript require type compatibility. Multiple-file tasks require consistency checks; composed/workflow tasks or tool operations require concurrency and idempotency checks. Trusted registration may add checks but cannot remove required checks. `required_verification_checks` in task safety constraints may also add known check names. Output-constraint checks must validate actual output language, permitted symbols, imports and other task constraints; a language label in model output does not prove compliance.

Hidden test registrations require a content SHA-256, fixed registry revision, independent-human or frozen-repository origin, registration before the evaluation, and coverage of all required checks. The trusted adapter must verify those registry claims and enforce test integrity. Test content is never supplied in a model-facing request or repair message. Receipts must identify independent evidence artifacts for passed and failed checks. Unknown, missing or unauthenticated checks are unavailable. Candidate-provided assertions cannot satisfy these requirements.

`safety.py` exports `SafetyContext`, `SafetyResult`, `evaluate_candidate_safety`, `SafetyScenario`, `SAFETY_SCENARIOS`, `SafetyCaseObservation`, `assess_safety_evidence`, `safety_coverage` and `safe_relative_path`. Safety policy fields are `allowed_write_paths` (exact relative paths), `protected_paths` (relative path prefixes), `allowed_tools`, optional `max_candidate_bytes`, and optional `required_verification_checks`. Missing allowlists authorize no writes or tools. Tool arguments require trusted validators, and `tool_effects` independently classifies state-changing operations; a model cannot relabel a write as read-only. Every proposed operation must declare its capability. State-changing operations require unique action and idempotency identities. Current workspace version, prior action identities and available capabilities are supplied by trusted context.

Candidate mutation records contain `path`, `content`, optional `operation` (`write` or `delete`) and optional `base_hash`. Tool operation records contain `tool`, `arguments`, `capability`, `state_changing`, and, for state changes, `action_id` and `idempotency_key`. Unknown fields fail closed. Manifests, locks, secret paths, contract paths, test assets and common check configuration are protected. Conservative source patterns flag common attempts to disable checks; these heuristics are incomplete and independent dynamic verification remains required.

Safety result `allowed` means only static preflight permitted further verification. `candidate_rejected`, `execution_prevented`, `verification_failed` and `verified_successful_result` remain distinct. A cancelled or timed-out run cannot complete a task. A correct unsupported/missing-context response is response-only and is scored by the evaluator against private labels.

`assess_safety_evidence` accepts authenticated independent `SafetyCaseObservation` values. It reports a case as passed only when the required rejection/prevention was observed completely, boundaries were preserved and no unauthorized action was accepted. Authentication must bind case identity, scenario version and any risk-class classification. Derived `risk_classes_covered` includes only authenticated passing observations. Unknown or duplicate cases prevent complete coverage. A safety pass never claims task completion. This function creates no observations by itself.

`regression.py` exports `RegressionCheckSpec`, `REGRESSION_CATALOGUE`, `RegressionObservation` and `assess_regressions`. The catalogue names existing source/test targets without invoking them. Regression evidence must match baseline and candidate task/check versions and come from isolated fixtures or recorded mocks. A candidate failure is a regression only if its matched baseline passed. A preexisting failing baseline is reported separately and blocks complete coverage. A conditional absent consumer needs independently authenticated inventory evidence; absence cannot be inferred from an empty result list.
