# Integration and report contracts

All APIs below are source implementations, not evidence that an evaluation occurred. Missing concrete transports, fixtures and evidence authorities are deliberate integration gaps. No program in this delivery starts a server, runs a benchmark or activates a model.

## Admission and fixed experimental conditions

1. An independent custodian curates real tasks, registers immutable evaluator-owned hidden tests and retains their answers outside all model-visible corpora. `EvaluationTask.from_dict` accepts the versioned private task contract; `public_view` emits an explicit public projection.
2. Build `ManifestEntry.for_task` entries, retain a pinned `DatasetManifest.manifest_hash` outside model access and retain the historical `task_id -> immutable_task_hash` registry. `verify_manifest` checks both. An explicit empty first-release registry needs a custodian approval reference; it cannot silently erase earlier identity history.
3. Translate the entire authorized training/reference inventory into `CorpusRecord`s, retain its hash and independently attest completeness. `audit_splits` binds the evaluation inventory and corpus; scans exact duplicates, lexical near duplicates, project/template overlap and known evaluation lineage. Truncated scans cannot yield clean status.
4. Pre-register adapter identities, their ordering, actual verification fixture digests, seed, all budgets, hardware policy and expected result keys before looking at scores. Call `prepare_evaluation` with the pinned manifest, identity registry and split audit. It snapshots tasks and returns an immutable-identity `EvaluationPlan`; mutable JSON changes are detected by `validate_plan`.

`configuration.executor_arms` is an ordered array of the three complete adapter identities (kinds `deterministic`, `retrieval`, `custom_model`). `configuration.runtime_arms` maps `deterministic` and `custom_model` to the actual runtime adapter identities. `configuration.verification_fixtures` maps each task ID to `executor.fixture_digest(context)`. This digest binds immutable workspace version, capability inventory, tool names/effects, trusted tool-policy digest, registered hidden-test hashes/revisions and initial completed-action/idempotency sets. `comparison_conditions` records additional host-controlled fixture, documentation, ordering, warmup and measurement decisions. `expected_result_keys` is an explicit array of `[mode, arm_id, task_id]` triples; complete reports require exact coverage with no duplicates.

`prepare_evaluation` inserts seed, task inventory digest and split audit digest into the configuration. Use **that final `plan.configuration`**, not the original partial input, in reports and acceptance evidence. The evaluation ID hashes the manifest, evaluation implementation version and final configuration. A repeated experiment should pin a new repetition identifier in configuration; never silently pool repeated tasks as independent evidence.

## Executor services

`evaluate_executor(plan, adapter, context_factory=..., sandbox=None, observe=None, fixture_authority=None, cancelled=...)` evaluates one pinned arm. `compare_executor_arms(plan, adapters, **services)` requires all three named arms and pinned ordering.

`context_factory(task, evaluation_id, arm_id, attempt)` receives private trusted task metadata and must create/reset a disposable fixture for that exact arm and attempt. It returns `VerificationContext`, including `tool_policy_digest` and an independently issued `fixture_reset_receipt`. `ExecutorFixtureAuthority.authenticate_fixture(context, task_digest, adapter_identity)` validates current permissions, reset and initial snapshot against a trusted store. It is never built from candidate metadata. Invalid or absent evidence prevents inference dispatch. The hidden registry and verifier live outside the model's workspace/process visibility.

Each model request has an independent public JSON snapshot. All arms share input, context, tools, language, time/output limits, attempts and seed schedule. Executor-only mode forces external-call/token budgets to zero. Retry requests include only the previous inert candidate and deterministic seed, with no private verifier output. Total output tokens and elapsed time are bounded across attempts; the sandbox receives only remaining time. A trusted supervisor must enforce hard limits and cancellation because Python cannot interrupt arbitrary callbacks safely. Unknown enforcement never earns bounded-success credit.

`observe(task_id, attempt, candidate_hash, verification_result)` returns trusted `AttemptTelemetry` **after** independent verification. Measurements must include the complete attempt scope, failed work and verification overhead. The observer must not read usage from candidate metadata. `ReasoningTrace` requires an observer identity, explicit complete-call coverage, and explicit executable-solution lineage. No observed calls plus unobserved context lineage is unknown, not independent execution. Resource measurements require `measured_by` and explicit scope; hardware is supplied only when measured.

## Phase 1 deterministic bridge

`bridges/phase1-compiler.ts` imports the discovered `DeterministicExecutionCompiler` and its registry directly from Phase 1 source and only translates envelopes. See [data-and-baselines.md](data-and-baselines.md) for exported functions and the `phase1_contract`, `phase1_context`, `phase1_workspace` mappings. It does not launch a process or execute the produced operation. Python's `DeterministicCompilerBridge` is still the supervised transport boundary; a reviewed `CompilerAssurance` must pin implementation/version, supported transformations and purity guarantees. There is no fallback implementation of Phase 1 business logic.

## Phase 2 learned-model bridge

`ModelIdentity` pins model version, tokenizer version, checkpoint identity, context length and generation configuration, with optional parameter count and training manifest/count. Initialization is the randomly initialized model track. `LocalModelAdapter(model, generate=None, count_input_tokens=None)` returns unavailable without both injected callbacks.

`count_input_tokens` receives the complete JSON form of `ExecutionRequest`; it must count the actual Phase 2 serialized prompt, including wrappers and previous candidates. The `GenerationInvocation` carries the request, identity, max output tokens, monotonic deadline and cancellation callback. The generator must enforce those controls using its actual tokenizer and local worker. A `CandidateOutput` contains a candidate, unsupported/missing-context response, or integration error/unavailability. Candidate text, mutations, language and metadata are claims to be independently validated. No model architecture, checkpoint loading, tokenizer training or inference implementation is duplicated here.

The observed Phase 2 `InferenceResponse` includes status plus candidate/error; its candidate carries text, raw bytes, UTF-8 validity, generation information, model metadata and resources. A future adapter must explicitly encode/decode bytes, validate malformed output, preserve actual identity and stop reason, and map responses without treating decoding completion as task completion. Do not infer missing-context intent from an arbitrary infrastructure error. No Phase 2 dependency is imported by the Python package.

## Full Cognitive Runtime integration

`RUNTIME_INTEGRATION_STATUS` is `pending_actual_runtime_adapter`. `CognitiveRuntimeAdapter.run_workflow` is a protocol; no adapter to the production `Runtime` class is shipped. `evaluate_full_system` returns unavailable if either the adapter or independent authority is absent. An injected adapter still needs separate integration qualification before any production promotion.

The Runtime request receives public task/context, executor selection, fixed budget/seed, conditions digest and nonce. `RuntimeEvidenceAuthority.authorize_fixture` must prove fixture-only execution before dispatch. `authenticate_observation` must verify persisted Runtime lifecycle, lease, permission, cancellation, tool and external-call receipts, not self-reported flags. The baseline and model arms use identical task sets, permission inventory, budgets, retry limits, external reasoning allowance, initial snapshot and hidden criteria.

Stage observations cover goal interpretation, planning, context assembly, strategy selection, execution, verification, bounded repair, escalation and final completion. Repair/escalation may be independently observed as not needed. Full-system completion requires all appropriate stage receipts, matched independent candidate verification, resources and budget evidence. Observed external assistance is allowed within the declared full-system budget, but cannot be credited as independent custom-model capability.

Pass a post-verification `observe` callback for full-system total usage/cost, preserving the authenticated original external-call trace. Runtime telemetry collected before Phase 4 verification cannot account for later verifier costs or peak memory; without complete later telemetry these remain unavailable. A fixture workflow must not use live credentials, production databases or live Ads services.

## Phase 3 dataset and evaluation-record compatibility

Phase 3's example schema is `execution-example-v1`, with `TrainingExample`, `Provenance`, `UsageAuthorization` and project/template families. Its `execution-split-v1` `SplitManifest` uses train/validation/test assignments, sample hashes, grouping and reserved-family metadata. A training test split is not automatically this independently governed evaluation suite. Every translated record needs original manifest/hash, project/template labels, authorized purpose, evaluation-origin flag and lineage. Do not infer retrieval authorization from permission to train alone.

The training manifest's identity pins checkpoint training data. Phase 4's evaluation manifest pins held-out tasks and independent oracle registrations. Preserve both; never substitute one digest for the other. `ModelVersionRegistry.record_evaluation` and `EvaluationAttestation` were discovered in Phase 3 but are not called here. Any later attestation translator must use genuine completed evidence, actual checkpoint SHA, evaluator identity, both manifest identities and policy decision. Passing a training registry evaluation record does not activate a model.

## Costs, acceptance audit and report rendering

`total_attempt_cost` separately records inference, external reasoning, independent verification and other components. Each absent component stays null. A fully observed empty external-call list can establish external-call cost zero; absence of instrumentation cannot. Inference and external cost components must be disjoint to avoid double counting. `TrainingCost` requires a receipt for known cost. `lifecycle_cost` amortizes training only with an explicit positive task horizon; it never guesses hardware prices or amortization periods.

`apply_acceptance_audit` adds a false-acceptance observation only when an independent authority authenticates the original exact `TaskResult` digest. Apply audits before computing comparisons or signing acceptance evidence. The generator, baseline and model cannot supply this audit. Refusals or prevented actions without an acceptance decision may remain unaudited/null.

`build_report` creates a JSON-compatible dictionary. `render_json` and `render_markdown` return strings; callers choose an approved report destination. They do not write, upload, train or publish. Private candidate bodies, hidden-test text and diagnostic stdout are omitted from attempt rendering. Stable check statuses/evidence hashes, retrieval IDs/scores, model identities, task-level outcomes, attribution, metrics, safety failures, acceptance, limitations, missing measurements and reproduction metadata remain available. Reports are evaluator-only material, never model prompts or training examples.

Report statuses are `not_run`, `partial`, `completed`. A not-run report cannot contain task observations; an empty report cannot be completed; completed reports need exact preregistered result coverage. Completion of an observation run does not mean its dataset is complete, its tasks passed, or promotion is eligible. Eligible reports require matching evaluation, dataset, configuration and model pins and all acceptance gates passed. JSON schemas provide interoperability; native Python checks and independent receipt authentication provide the stronger semantic constraints.

Reproduction metadata should include repository revision and relevant source hashes, Python/OS versions, actual hardware measurement receipt, task/corpus/hidden-test registry pins, adapter/compiler/tokenizer/checkpoint identities, generation parameters, seed, fixture/reset/tool-policy versions, arm order, sampling design, budgets, measurement scopes, cost-rate receipts, evaluator version and actual timestamps. Unknown entries must remain null or explicitly absent with a stated limitation. No report with fabricated observations is included in this delivery.

## Phase 5 promotion and rollback

`assess_promotion` can emit `promotion_eligible` only after all configured independent gates pass. Missing receipts/authentication leave gates pending or failed. `eligibility_handoff` validates checkpoint/decision binding and emits an inert proposal with `activation_authorized=false`. Phase 5 must reauthenticate original evidence, obtain separate operator authorization, pin the exact checkpoint/tokenizer/policy, run independently verified full-system qualification, keep the last known good routing/checkpoint, use a bounded rollout and independently verify rollback. No function in this package deploys, activates, merges, modifies Runtime routing or writes evaluation failures into training data.
